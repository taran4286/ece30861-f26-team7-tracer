# tester/: our tester

Our tester service, implementing `tester-openapi.yaml`. `server.py` mounts `tester_app` at `/tester`, its own base URL. Root "Directory guides" says which file wins when this one disagrees with the root `AGENTS.md` or `tester-openapi.yaml`.

## What it serves

- `GET /` returns an HTML page with `tester.png` inlined and captioned "Team 7 tester", so a browser shows the deploy is up; `/tester` without the slash redirects there with a 307. It's outside the spec, and reads the photo per request, so a missing file breaks only this page.
- `GET /test/report?session_id=` returns the stored `SuiteReport` of a finished or aborted run and never starts or repeats one. A missing or blank `session_id` gets 400, an unknown session 404, a session whose run hasn't ended 409, and unreachable storage 500, each with `source: "tester"`.
- Any other GET, POST, PUT, PATCH or DELETE request, including the spec's `/test/setup` and `/test/run`, returns 501 `{"message": "/<path> is not implemented", "source": "tester"}`, the spec's `TestControlError` shape.
- GET and HEAD on FastAPI's generated `/docs`, `/docs/oauth2-redirect`, `/redoc` and `/openapi.json` also answer, and other methods such as `HEAD` and `OPTIONS` elsewhere get FastAPI's 405; both are outside the spec.

## Session storage

Sessions and reports live in Postgres, in the `tester_sessions` table, reached as the tester role through `TESTER_DATABASE_URL` (root "Database roles"). Setup, run and report lookups can each land on a different Vercel instance, so memory or `/tmp` would lose them.

| Module | Provides |
| --- | --- |
| `config.py` | `TesterSettings` (`tester_database_url`) through the cached `get_tester_settings()` |
| `db.py` | `Base`, the cached `get_engine()` and `transaction()`, mirroring `app/db.py` |
| `models.py` | `StoredSession`, the `tester_sessions` table, and `RunStatus` |
| `sessions.py` | `create_session`, `start_run`, `finish_run`, `get_report`, and `ControlError(status, message, source="tester")` |

`tester_sessions` has one row per session: `session_id` (text primary key, generated by the tester), `target_url`, `status`, `report` (JSONB, SQL NULL until the run ends), `created_at` and `finished_at`. A session's `status` moves only forward:

1. `create_session` stores it as `ready`. Call it only after the target's setup succeeds, so a failed setup stores nothing.
2. `start_run` moves `ready` to `running` in one `UPDATE … WHERE status = 'ready'`, so of two simultaneous calls only one starts the run. The other gets 409; an unknown session gets 404.
3. `finish_run` stores the report and moves `running` to `finished` or `aborted`, committing before it returns. It changes only a running session, so a stored report is never replaced; any other call is a tester bug and raises 500.
4. `get_report` returns the stored report: 404 for an unknown session, 409 while it's `ready` or `running`.

## Rules

- Never import `app`. The tester checks systems, ours included, only through their HTTP API; `tests/test_tester.py` fails on any `app` import here.
- Test-control errors carry `message` and `source`, never the project `Error` schema.
- The 501 catch-all matches every path, so declare every other route before it.
- Each storage function is one short transaction. A run never holds a transaction open while it calls the target.
- Settings are read on first use, not at import, so the tester still loads without `TESTER_DATABASE_URL`. Preview deployments don't have it, so the report route answers 500 there.
- `get_tester_settings()`, `get_engine()` and `_session_factory()` are cached. A test that changes `TESTER_DATABASE_URL` clears all three before and after.
- Nothing here creates tables; the tester role can't. `scripts/setup_db.py` creates `tester_sessions` from `models.py`, and a new tester table also needs a `TESTER_GRANTS` entry there. Changing a column needs a wiped local database or a migration, as for the app's tables (root "Local setup steps").
