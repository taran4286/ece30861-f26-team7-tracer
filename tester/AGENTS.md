# tester/: our tester

Our tester service, serving the routes in `tester-openapi.yaml`. `server.py` mounts `tester_app` at `/tester`, its own base URL.

## What it serves

- `GET /` returns an HTML page (`pages.py`): the title "Team 7 — Tracer tester", how to run setup, run and report with the time limits, and a form whose `?session_id=` shows that session's stored report as tables: totals, per-criterion counts, coverage, and every test with its message. Without a session ID it never touches storage, so it also loads on previews; an unknown or unfinished session, or unreachable storage, shows why there's no report. It only reads reports, never starts a run. `/tester` without the slash redirects there with a 307.
- `POST /test/setup` with `{target_url}` prepares a session on the target and returns 201 `{session_id}` (see "Setup and run"). A `target_url` that isn't an http or https system base URL, or that has a `/test` suffix, a query, a fragment or credentials, gets 400. A target error (400 or above) is passed on with its status, message and source, with `source: "system"` when its body isn't a `TestControlError`. No answer within 20 s, or a connection or transport error, gets 500 with `source: "communication"`. A status below 400 other than 201, or a 201 that doesn't name our session ID, gets 500 with `source: "system"`.
- On setup and run, a body that isn't a JSON object gets 400 "Expected a JSON object body".
- `POST /test/run` with `{session_id}` runs every planned case once and returns 200 with the stored `SuiteReport`, failed tests included. A missing or blank `session_id` gets 400, an unknown session 404, and a session that has already started 409. An aborted run stores its partial report and gets 500 with `source: "tester"`.
- `GET /test/report?session_id=` returns the stored `SuiteReport` of a finished or aborted run and never starts or repeats one. A missing or blank `session_id` gets 400, an unknown session 404, and a session whose run hasn't ended 409.
- On all three, unreachable storage gets 500 "Tester storage is unavailable" and any other fault in our code 500 "Tester fault: …", both with `source: "tester"`.
- Any other GET, POST, PUT, PATCH or DELETE request returns 501 `{"message": "/<path> is not implemented", "source": "tester"}`.
- GET and HEAD on FastAPI's generated `/docs`, `/docs/oauth2-redirect`, `/redoc` and `/openapi.json` also answer, and other methods such as `HEAD` and `OPTIONS` elsewhere get FastAPI's 405.

## Session storage

Sessions and reports live in Postgres, in the `tester_sessions` table, reached as the tester role through `TESTER_DATABASE_URL` (root "Database roles"). Setup, run and report lookups can each land on a different Vercel instance, so memory or `/tmp` would lose them.

| Module | Provides |
| --- | --- |
| `config.py` | `TesterSettings` (`tester_database_url`) through the cached `get_tester_settings()` |
| `db.py` | `Base`, the cached `get_engine()` and `transaction()`, mirroring `app/db.py`, including `parse_url()`, which makes a malformed `TESTER_DATABASE_URL` an `ArgumentError` the storage handlers catch |
| `models.py` | `StoredSession`, the `tester_sessions` table, and `RunStatus` |
| `sessions.py` | `create_session`, `start_run`, `finish_run`, `get_report`, and `ControlError(status, message, source="tester")` |

`tester_sessions` has one row per session: `session_id` (text primary key, generated by the tester), `target_url`, `status`, `report` (JSONB, SQL NULL until the run ends), `created_at` and `finished_at`. A session's `status` moves only forward:

1. `create_session` stores it as `ready`. Call it only after the target's setup succeeds, so a failed setup stores nothing.
2. `start_run` moves `ready` to `running` in one `UPDATE … WHERE status = 'ready'`, so of two simultaneous calls only one starts the run. The other gets 409; an unknown session gets 404.
3. `finish_run` stores the report and moves `running` to `finished` or `aborted`, committing before it returns. It changes only a running session, so a stored report is never replaced; any other call is a tester bug and raises 500.
4. `get_report` returns the stored report: 404 for an unknown session, 409 while it's `ready` or `running`.

## Setup and run

`runner.py` does the work behind the setup and run routes, which call it in FastAPI's thread pool because it blocks on the target and the database.

- `prepare(target_url)` generates a session ID (`t7-` and a UUID), sends `{session_id, setup: {}}` to the target's `/test/setup` with a 20 s timeout (`SETUP_TIMEOUT_SECONDS`, from `client.py`), and stores the session as `ready` only after a 201 that names that ID.
- `run_session(session_id)` builds the case list with `planned()`, starts the run with `start_run`, runs the cases through `run_cases`, builds the report and checks it with `report_problems`, then stores it with `finish_run`. Planning reads the fixture files, so it comes before `start_run`: if it fails, the session stays `ready`.
- The run's `Target` gets a deadline 105 s after the run starts (`CALL_CUTOFF_SECONDS`), leaving room inside the 130 s run limit the page states. After it, `Target.call` sends nothing and raises `Stopped`; `run_cases` records that case as an `error` from the tester and every later case as `skip`, and the run is aborted. The coverage request isn't held to the deadline.
- Coverage counts what the run exercised, not what passed:
  - `code` is the target's own measure from `GET /test/report?session_id=`. It becomes null counts with the reason in `basis` when that request gets no answer, a status other than 200, a body that breaks the spec, or more covered than total.
  - `component` counts the system spec's 7 tags with at least one request in `Target.called`.
  - `system` counts the criteria, by test ID prefix, with at least one case not skipped.
- `report_problems` checks a report against `SuiteReport` in `tester-openapi.yaml`, plus the rules the schema can't express: every planned test appears once, test IDs are unique, and `covered` is never above `total`. A report that fails is a tester bug: it's stored as `aborted` and the run gets 500.
- A fault after `start_run` outside the cases, the report check included, also stores an aborted report, with the cases' results if they all ran and every case skipped otherwise, so the session never stays `running`.

## Cross-team test cases

`cases.planned()` lists every case in run order. `runner.run_session` runs them against a prepared session, and `tests/test_tester_cases.py` runs them against `tests/fake_system.py`.

| Module | Does |
| --- | --- |
| `client.py` | `Target`: sends a call to the target's base URL with `X-Test-Run`, `X-User-Id` and `X-User-Role` and a 10 s timeout, no retry, and checks the reply against the spec. `X-Test-Run` is the run's session unless the call names another (`session=`). It records each (method, template) it sends in `called`, refuses calls after its deadline with `Stopped`, and asks for the session's coverage report with `coverage()`. Its test-control calls, which carry no identity headers, are `snapshot()`, `settings()` (`PATCH /test/sessions/{session_id}/settings`) and `setup()` (`POST /test/setup`, with the 20 s setup timeout). Each `Reply` carries `sent_at` and `received_at`, the tester's UTC clock just before and after the call. `Actor` holds the identity headers |
| `spec.py` | Loads `system-openapi.yaml` and `tester-openapi.yaml` from the repo root and checks JSON against their schemas, `date` and `date-time` formats included; also gives the system spec's tags and each operation's tags |
| `suite.py` | `run_cases()`, the outcome rules (a `Stopped` case is an error from the tester and the rest are skipped), `expect()`, and `Run`: one session's shared setups (`once`, `forget`), its snapshot baseline for "stored data unchanged" checks, `set_clock()`, and `prepare()`, which prepares another session on the target and returns a `Run` acting in it |
| `business_days.py` | The tester's own business-day calendar from `holidays.UnitedStates(observed=True)`: `add_business_days(start, days=4)`, the start day not counted |
| `cases.py` | The cases, by criterion: AC-02, 03, 07, 08, 20, 14, 12, 13, 15, 06, 09 (a), 23 (a)–(c), then 01, each with normal cases and edge cases |

- Outcomes: `pass` when the reply meets the pass rule, an expected 403, 404 or 409 included. `fail` when it doesn't, including a body that breaks its spec schema and a 501 on a route the case needs. `error` with `source: system` for any other 5xx, `communication` when no response arrives, and `tester` for a fault in our code. `skip` for a case not run.
- `expect()` accepts an error `field` equal to the expected one or nested under it (`expected[…` or `expected.…`, via `field_matches`), so `items[0].ticket_id` passes where `items[0]` is expected.
- A shared setup that fails, such as the incident several cases use, gives each of those cases the same outcome. A failure or a target error is reported with its message starting `Setup failed:`; anything else (a tester fault, `Skip`, `Stopped`) is re-raised as it was, so a tester fault in a setup reads "Tester fault: …".
- "Stored data unchanged" compares the target's snapshot (`GET /test/report/{run_id}`) before and after the call, with arrays sorted by ID.
- "Real server time" (AC-02's `imported_at`, AC-23's audit `timestamp`) is checked by `clock_problems` against the tester's own clock: the value must fall between `sent_at` minus 5 s and `received_at` plus 5 s. Never use the response's `Date` header; a host can send a stale one, as a Vercel function does on its first reply after sitting idle.
- AC-06 runs all 49 state pairs. Each allowed move goes through the route the spec's state table gives it: `/determination`, `/transitions`, or `/filings` with the incident's `required_form` (8-K Item 1.05 from DeterminedMaterial and DisclosureDelayed, 8-K/A from AmendmentPending). Each refused pair goes through `/transitions` with `to` set and an otherwise valid body. `incident_in` reaches DisclosureRecorded with a Material determination and an 8-K filing listing `impact` as unavailable, and AmendmentPending with a further transition (`info_available_date` today, `elements: ["impact"]`). A source state's allowed moves run after its refused ones, and a case that sees the incident leave its state calls `run.forget`, so later cases get a new one. AC-06 also has 10 cases outside the 49 pairs: UnderAssessment to either Determined state through `/transitions`, each of the three filing moves through `/transitions`, DeterminedNotMaterial to DeterminedMaterial through `/determination`, Responder and Board forbidden, an unknown target state, and an unknown incident.
- Cases that need another date (AC-12's flags, AC-13's flags, AC-15's transition) move the session's clock inside `clock_at(run, day)`, which sets `test_now` to 15:00 UTC on that day with `Run.set_clock` and sets it back to `SETUP_TEST_NOW` however the block ends: later cases share the session and assume `TODAY`. A failed reset fails the case unless the block already failed it. `set_clock` fails unless the reply is a 200 `TestRun` naming the session and the time sent.
- Registrant type is fixed per session, so AC-13 prepares a second session, `<session_id>-fpi` with `setup: {"registrant_type": "FPI"}`, through `Run.prepare`, and acts in it through the `Run` that returns: its calls carry that session's `X-Test-Run`, its snapshots and clock are that session's, and it shares the target's deadline and `called`. Code coverage still comes from the run's own session.
- Expected due dates (AC-12, AC-15) are the dates the criteria state, and `expected_due` checks each against `business_days.add_business_days`; a disagreement is a tester fault. Flag checks compare the incident's `warning` and `overdue` with exactly the expected set, since the spec checks them in order and at most one applies.
- Each filing gets an accession number distinct within its session, from `accession(run)`.
- AC-01 runs last, so its 100 incidents don't enlarge every earlier snapshot.

## Rules

- Never import `app`. The tester checks systems, ours included, only through their HTTP API; `tests/test_tester.py` fails on any `app` import here.
- Test-control errors carry `message` and `source`, never the project `Error` schema.
- HTML-escape everything `pages.py` shows from a report or the query: messages quote other teams' systems.
- The 501 catch-all matches every path, so declare every other route before it.
- Each storage function is one short transaction. A run never holds a transaction open while it calls the target.
- Settings are read on first use, not at import, so the tester still loads without `TESTER_DATABASE_URL`. Preview deployments don't have it, so setup, run and report answer 500 there; setup does so after the target has already prepared its session, since it stores ours only afterwards.
- `get_tester_settings()`, `get_engine()` and `_session_factory()` are cached. A test that changes `TESTER_DATABASE_URL` clears all three before and after.
- Nothing here creates tables; the tester role can't. `scripts/setup_db.py` creates `tester_sessions` from `models.py`, and a new tester table also needs a `TESTER_GRANTS` entry there. Changing a column needs a wiped local database or a migration, as for the app's tables (root "Local setup steps").
- Expected statuses, error codes and fields come from `system-openapi.yaml`, and each case's pass rule from its course acceptance criterion. For example, Responder and Board get 403 on the audit and delete routes, and only a DisclosureApprover gets 405.
- Each rejection case's request has exactly one thing wrong with it, so its expected error doesn't depend on the order a system checks errors in. A refused move to AmendmentPending sends `info_available_date` today and `elements: ["impact"]`, a subset of the latest filing's `unavailable_elements` wherever the incident has a filing.
- Dates in the cases assume the session's `test_now` is the setup default, `SETUP_TEST_NOW` (2026-10-05T15:00:00Z, whose date is `TODAY` in `cases.py`), so the runner's setup must send `setup: {}`, and a case may move the clock only inside `clock_at`.
- Make every project call through `Run.call`, never `Target.call`, and every test-control call through `Run`'s `snapshot`, `set_clock` and `prepare`: `call` and `set_clock` end the saved snapshot baseline, so a rejection is never compared with stale data.
- Build HTTP clients for a target only through `runner.client_for`, so tests can serve `FakeSystem` there instead of the network.
- Test IDs are stable and unique, and start with their criterion (`AC-06-DM-to-Closed`); reports from both teams are compared by them.
- `spec.py` reads `system-openapi.yaml` and `tester-openapi.yaml`, and `planned()` reads `fixtures/`, on first use, not at import, so a missing file fails only the run, not the app.
