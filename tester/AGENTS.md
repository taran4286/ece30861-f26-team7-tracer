# tester/: our tester

Our tester service, serving the routes in `tester-openapi.yaml` and an LLM stub. `server.py` mounts `tester_app` at `/tester`, its own base URL.

## What it serves

- `GET /` returns an HTML page (`pages.py`): the title "Team 7 — Tracer tester", how to run setup, run and report with the time limits, and a form whose `?session_id=` shows that session's stored report as tables: totals, per-criterion counts, coverage, and every test with its message. Without a session ID it never touches storage, so it also loads on previews; an unknown or unfinished session, or unreachable storage, shows why there's no report. It only reads reports, never starts a run. `/tester` without the slash redirects there with a 307.
- `POST /test/setup` with `{target_url}` prepares a session on the target and returns 201 `{session_id}` (see "Setup and run"). A `target_url` that isn't an http or https system base URL, or that has a `/test` suffix, a query, a fragment or credentials, gets 400. A target error (400 or above) is passed on with its status, message and source, with `source: "system"` when its body isn't a `TestControlError`. No answer within 20 s, or a connection or transport error, gets 500 with `source: "communication"`. A status below 400 other than 201, or a 201 that doesn't name our session ID, gets 500 with `source: "system"`.
- On setup and run, a body that isn't a JSON object gets 400 "Expected a JSON object body".
- `POST /test/run` with `{session_id}` runs every planned case once and returns 200 with the stored `SuiteReport`, failed tests included. The run gives the target LLM stub URLs under the tester's base URL as the caller reached it (`public_url`): the scheme and host from `X-Forwarded-Proto` and `X-Forwarded-Host`, which Vercel's proxy sets, or from the request without them, then the mount's `root_path`. A missing or blank `session_id` gets 400, an unknown session 404, and a session that has already started 409. An aborted run stores its partial report and gets 500 with `source: "tester"`.
- `GET /test/report?session_id=` returns the stored `SuiteReport` of a finished or aborted run and never starts or repeats one. A missing or blank `session_id` gets 400, an unknown session 404, and a session whose run hasn't ended 409.
- On all three, unreachable storage gets 500 "Tester storage is unavailable" and any other fault in our code 500 "Tester fault: …", both with `source: "tester"`.
- `POST /llm/fail/chat/completions`, `POST /llm/silent/chat/completions`, `POST /llm/reply/{content}/chat/completions` and `POST /llm/reply/chat/completions` are the LLM stub (see "LLM stub").
- Any other GET, POST, PUT, PATCH or DELETE request returns 501 `{"message": "/<path> is not implemented", "source": "tester"}`, the stub's paths with another method included.
- GET and HEAD on FastAPI's generated `/docs`, `/docs/oauth2-redirect`, `/redoc` and `/openapi.json` also answer, and other methods such as `HEAD` and `OPTIONS` elsewhere get FastAPI's 405.

## Session storage

Sessions and reports live in Postgres, in the `tester_sessions` table, reached as the tester role through `TESTER_DATABASE_URL` (root "Database roles"). Setup, run and report lookups can each land on a different Vercel instance, so memory or `/tmp` would lose them.

| Module | Provides |
| --- | --- |
| `config.py` | `TesterSettings` (`tester_database_url`, `tester_own_system_url`) through the cached `get_tester_settings()`; the own-system URL defaults to Team 7's production `/system` and rejects credentials, query strings and fragments |
| `db.py` | `Base`, the cached `get_engine()` and `transaction()`, mirroring `app/db.py`, including `parse_url()`, which makes a malformed `TESTER_DATABASE_URL` an `ArgumentError` the storage handlers catch |
| `models.py` | `StoredSession`, the `tester_sessions` table, and `RunStatus` |
| `sessions.py` | `create_session`, `start_run`, `finish_run`, `get_report`, and `ControlError(status, message, source="tester")` |

`tester_sessions` has one row per session: `session_id` (text primary key, generated by the tester), `target_url`, `status`, `report` (JSONB, SQL NULL until the run ends), `created_at` and `finished_at`. A session's `status` moves only forward:

1. `create_session` stores it as `ready`. Call it only after the target's setup succeeds, so a failed setup stores nothing.
2. `start_run` moves `ready` to `running` in one `UPDATE … WHERE status = 'ready'`, so of two simultaneous calls only one starts the run. The other gets 409; an unknown session gets 404.
3. `finish_run` stores the report and moves `running` to `finished` or `aborted`, committing before it returns. It changes only a running session, so a stored report is never replaced; any other call is a tester bug and raises 500.
4. `get_report` returns the stored report: 404 for an unknown session, 409 while it's `ready` or `running`.

## Setup and run

`runner.py` does the work behind the setup and run routes, which call it in FastAPI's thread pool because it blocks on the target and the database.

- `prepare(target_url)` generates a session ID (`t7-` and a UUID), sends `{session_id, setup: {}}` to the target's `/test/setup` with a 20 s timeout (`SETUP_TIMEOUT_SECONDS`, from `client.py`), and stores the session as `ready` only after a 201 that names that ID.
- `run_session(session_id, tester_url)` builds the case list with `planned()`, starts the run with `start_run`, runs the cases through `run_cases`, builds the report and checks it with `report_problems`, then stores it with `finish_run`. `run_cases` hands `tester_url` to the run's `Run`. Planning reads the fixture files, so it comes before `start_run`: if it fails, the session stays `ready`.
- The run's `Target` gets a deadline 105 s after the run starts (`CALL_CUTOFF_SECONDS`), leaving room inside the 130 s run limit the page states. After it, `Target.call` sends nothing and raises `Stopped`; `run_cases` records that case as an `error` from the tester and every later case as `skip`, and the run is aborted. The coverage request isn't held to the deadline.
- Coverage counts what the run exercised, not what passed:
  - `code` is the target's own measure from `GET /test/report?session_id=`. It becomes null counts with the reason in `basis` when that request gets no answer, a status other than 200, a body that breaks the spec, or more covered than total.
  - `component` counts the system spec's 7 tags with at least one request in `Target.called`.
  - `system` counts the criteria, by test ID prefix, with at least one case not skipped.
  - `model` is included only for the configured own-system URL (see Model coverage). It is omitted for cross-team targets.
- `report_problems` checks a report against `SuiteReport` in `tester-openapi.yaml` and the local model-measure extension, plus the rules the schema can't express: every planned test appears once, test IDs are unique, `covered` is never above `total`, and model coverage is present exactly for self-tests. A report that fails is a tester bug: it's stored as `aborted` and the run gets 500.
- A fault after `start_run` outside the cases, the report check included, also stores an aborted report, with the cases' results if they all ran and every case skipped otherwise, so the session never stays `running`.

## Model coverage

- `model_coverage.json` is the versioned Team 7 design-to-test mapping (`team7-phase5-design-v1`), derived from the linked Phase 2 requirements/models and its Phase 5 milestone. Its `P5-D` IDs identify this team's design constraints, not extra pod requirements. The mapping itself states the milestone scope, exact test IDs and evaluation gaps.
- `model_coverage.py` loads the mapping on use and validates that its test IDs exist in the planned suite. A stale or unreadable mapping aborts a self-test with a stored report; model counts are null/null with a reason if measurement could not be completed. Cross-team runs do not read this mapping.
- A design requirement counts only when its nonempty list of mapped tests all reach `pass` or `fail` in this session. Neither `skip` nor `error` counts, nor a failure before evaluation caused by shared setup or an unsettled reset. Counts indicate evaluation, not correctness. The basis names the design version, links the mapping and lists the counted IDs. FPI subject preparation and acceptance isolation-session preparation use `Run.once`, so prerequisite rejections are marked as setup failures and cannot count as evaluated design checks.
- The mapping has 14 requirements. Two are intentionally unmapped: the real 60-second no-response timeout and independent review of real-model prose. FPI drafting and advisory draft acceptance are exercised by explicit cases. Separate local pytest checks and human review are not executed by this suite and are not added to its counts. A fully evaluated 250-case suite covers 12/14; a partial run can cover fewer.
- Self identity compares the whole target base URL with `TESTER_OWN_SYSTEM_URL`, normalizing scheme/host case, default ports and a trailing slash. It never uses the caller's forwarded host or tester URL to infer ownership. The configured value defaults to the registered production system URL; override it for a local self-test. Other Team 7 aliases must be configured explicitly to count as self-tests.
- `spec.report_errors` validates any present model measure using the shared `CoverageMeasure` schema without modifying the pod's shared YAML copies. `runner.report_problems` enforces self-only inclusion. The page already renders every supplied coverage measure. Finalized stored reports, including older ones without model coverage, are read back unchanged.

## LLM stub

`stub.py` is an OpenAI-compatible chat completions endpoint for a session's `llm_base_url` (TEST-07's settings update sets it on a target). A system posts to `{llm_base_url}/chat/completions`, so each mode is a base URL under the tester's own, built by `fail_url`, `silent_url` and `reply_url` from the tester's base URL:

| Base URL | Answer |
| --- | --- |
| `{tester}/llm/fail` | 500 at once, `{"error": {"message", "type": "server_error"}}` |
| `{tester}/llm/silent` | 504 after `SILENT_SECONDS` (65 s), past the spec's 60 s plus AC-21's 2 s |
| `{tester}/llm/reply/{content}` | 200 chat completion whose `choices[0].message.content` is `content` |
| `{tester}/llm/reply` | the same with empty content |

- `reply_url(tester_url, content)` encodes `content` as unpadded base64url of its UTF-8, or gives `{tester}/llm/reply` for empty content, which has no segment to encode, so the caller decides exactly what the model says, malformed replies included. A segment that isn't that encoding, decodes to invalid UTF-8 or exceeds `MAX_CONTENT_BYTES` (8,000) decoded gets 400 `{"error": {"message", "type": "invalid_request_error"}}`.
- The stub ignores the request body and headers and stores nothing, so any instance answers any call.
- Its routes are async, so the silent mode holds no worker thread while it waits.

## Cross-team test cases

`cases.planned()` lists every case in run order. `runner.run_session` runs them against a prepared session, and `tests/test_tester_cases.py` runs them against `tests/fake_system.py`.

| Module | Does |
| --- | --- |
| `client.py` | `Target`: sends a call to the target's base URL with `X-Test-Run`, `X-User-Id` and `X-User-Role` and a 10 s timeout, no retry, and checks the reply against the spec. `X-Test-Run` is the run's session unless the call names another (`session=`). It records each (method, template) it sends in `called`, refuses calls after its deadline with `Stopped`, and asks for the session's coverage report with `coverage()`. Its test-control calls, which carry no identity headers, are `snapshot()`, `settings()` (`PATCH /test/sessions/{session_id}/settings`) and `setup()` (`POST /test/setup`, with the 20 s setup timeout). Each `Reply` carries `sent_at` and `received_at`, the tester's UTC clock just before and after the call. `Actor` holds the identity headers |
| `spec.py` | Loads `system-openapi.yaml` and `tester-openapi.yaml` from the repo root and checks JSON against their schemas, `date` and `date-time` formats included; also gives the system spec's tags and each operation's tags |
| `suite.py` | `run_cases()`, the outcome rules (a `Stopped` case is an error from the tester and the rest are skipped), `expect()`, and `Run`: one session's shared setups (`once`, `forget`), its snapshot baseline for "stored data unchanged" checks, `set_clock()`, `set_llm()` (the session's `llm_base_url`, failing unless the target's `TestRun` confirms it), `tester_url` (where the target reaches the LLM stub; a case that needs it is a tester fault without it), and `prepare()`, which prepares another session on the target and returns a `Run` acting in it |
| `business_days.py` | The tester's own business-day calendar from `holidays.UnitedStates(observed=True)`: `add_business_days(start, days=4)`, the start day not counted |
| `cases.py` | The cases, by criterion: AC-21 (a) and (c), 02, 03, 07, 08, 20, 14, 12, 13, 15, 06, 09 (a) and (c), 23 (a)–(c), 04, 05, 19, 16, 17, 18, then 01, each with normal cases and edge cases |

- Outcomes: `pass` when the reply meets the pass rule, an expected 403, 404 or 409 included. `fail` when it doesn't, including a body that breaks its spec schema and a 501 on a route the case needs. `error` with `source: system` for any other 5xx, `communication` when no response arrives, and `tester` for a fault in our code. `skip` for a case not run.
- `expect()` accepts an error `field` equal to the expected one or nested under it (`expected[…` or `expected.…`, via `field_matches`), so `items[0].ticket_id` passes where `items[0]` is expected.
- A shared setup that fails, such as the incident several cases use, gives each of those cases the same outcome. A failure or a target error is reported with its message starting `Setup failed:`; anything else (a tester fault, `Skip`, `Stopped`) is re-raised as it was, so a tester fault in a setup reads "Tester fault: …".
- "Stored data unchanged" compares the target's snapshot (`GET /test/report/{run_id}`) before and after the call, with arrays sorted by ID.
- "Real server time" (AC-02's `imported_at`, AC-23's audit `timestamp`) is checked by `clock_problems` against the tester's own clock: the value must fall between `sent_at` minus 5 s and `received_at` plus 5 s. Never use the response's `Date` header; a host can send a stale one, as a Vercel function does on its first reply after sitting idle.
- AC-06 runs all 49 state pairs. Each allowed move goes through the route the spec's state table gives it: `/determination`, `/transitions`, or `/filings` with the incident's `required_form` (8-K Item 1.05 from DeterminedMaterial and DisclosureDelayed, 8-K/A from AmendmentPending). Each refused pair goes through `/transitions` with `to` set and an otherwise valid body. `incident_in` reaches DisclosureRecorded with a Material determination and an 8-K filing listing `impact` as unavailable, and AmendmentPending with a further transition (`info_available_date` today, `elements: ["impact"]`). A source state's allowed moves run after its refused ones, and a case that sees the incident leave its state calls `run.forget`, so later cases get a new one. AC-06 also has 10 cases outside the 49 pairs: UnderAssessment to either Determined state through `/transitions`, each of the three filing moves through `/transitions`, DeterminedNotMaterial to DeterminedMaterial through `/determination`, Responder and Board forbidden, an unknown target state, and an unknown incident.
- Cases that need another date (AC-12's flags, AC-13's flags, AC-15's transition) move the session's clock inside `clock_at(run, day)`, which sets `test_now` to 15:00 UTC on that day with `Run.set_clock` and sets it back to `SETUP_TEST_NOW` however the block ends: later cases share the session and assume `TODAY`. If the block passed, a failed reset fails the case, or makes it an `error` when the reset gets a 5xx or no answer. If the block already failed, the reset's failure is added to that message. `set_clock` fails unless the reply is a 200 `TestRun` naming the session and the time sent.
- Registrant type is fixed per session, so AC-13 prepares a second session, `<session_id>-fpi` with `setup: {"registrant_type": "FPI"}`, through `Run.prepare`, and acts in it through the `Run` that returns: its calls carry that session's `X-Test-Run`, its snapshots and clock are that session's, and it shares the target's deadline and `called`. Code coverage still comes from the run's own session.
- Expected due dates (AC-12, AC-15) are the dates the criteria state, and `expected_due` checks each against `business_days.add_business_days`; a disagreement is a tester fault. Flag checks compare the incident's `warning` and `overdue` with exactly the expected set, since the spec checks them in order and at most one applies. AC-12's filing case first requires `overdue`, so a system without flags can't pass it by having nothing to clear.
- Each filing gets an accession number distinct within its session, from `accession(run)`.
- AC-01 runs last, so its 100 incidents don't enlarge every earlier snapshot.
- The session's LLM is down for every case that doesn't draft (AC-21 (c)): the first case sets `llm_base_url` to the stub's fail URL with `Run.set_llm`, AC-13's FPI session is prepared with it, and a case that drafts changes it only inside `llm_at(run, content)`, which points it at a reply stub saying `content` (a dict sent as JSON) and sets it back to the fail URL however the block ends, with `clock_at`'s failure rules. A reset the target doesn't confirm stays the run's `pending_reset`, which `run_cases` makes (`Run.settle`) before the next case runs; if it fails again, that case fails or errors with "Before this case, an earlier case's reset failed again", and the next one tries once more. AC-21 (a) drafts against the fail stub and a non-JSON reply and requires 503 `DRAFTING_UNAVAILABLE`, message exactly "Drafting unavailable", within 5 s of the tester's own clock. AC-21 (b), no answer within 60 s, has no case: it needs one call to wait past the pod's 10 s project call limit.
- A reply stub's content is the four elements, each `{text, citations, sensitive_flags}` as in the spec's `DraftElement`, so the drafting cases assume a target asks its LLM for that JSON. `material` makes a Material incident from ticketing items in the run's registrant type, and `drafting_subject` is the one shared by AC-21, AC-09 (c) and fault cases.
- Every 201 draft is checked by `structure_problems` (this incident, `form_type` 8-K Item 1.05 (6-K for the FPI case), Proposed, each element with text, no key named `materiality` anywhere) and `citation_problems` (drafted text cites at least one of the incident's evidence IDs and nothing else; "Not yet determined" with no citations or flags). AC-16 checks the delivered structure and citations without demanding verbatim provider text; the explicit no-evidence impact cases still require the exact missing-information marker. Real prose quality is evaluated separately by reviewers. Its synthetic ticket summaries support those exact texts; the absent-impact tickets explicitly record that no measured impact is available. AC-17's additional incidents likewise have evidence for their nature, scope and timing. AC-18 creates a separate subject per four-text batch with supporting tickets for all four samples, so a target is never asked to pass through prose unsupported by its fixtures. A reply a system must not pass on as sent (an element missing, a `materiality` key, a citation of another incident's or an unknown evidence ID, uncited text) passes with either a 503 "Drafting unavailable" or a 201 draft that keeps those rules without it, and the incident's state and version must be unchanged after it. AC-09 (c)'s normal draft also keeps the incident's determination.
- AC-16's 10 incidents have four tickets each, the model citing one per element and leaving impact "Not yet determined" in drafts 3, 6 and 9; AC-17 (a) checks the citations of the same drafts, and AC-17 (b)'s 5 more incidents have three tickets and an impact the model leaves "Not yet determined", which must come back exactly so.
- AC-18 reads the 20 labeled texts in `fixtures/evaluation/sensitive_texts.json` (10 with `expected_sensitive`; any other split is a tester fault) and supplies each four-text batch as paragraphs of the nature element, citing the batch's supporting evidence. Other elements remain "Not yet determined", so field-specific impact rewriting does not prevent this scanner experiment. A text counts as flagged when a nonempty reported excerpt is inside that text or covers it; an excerpt covering a whole batch counts for each text it covers. Each of those drafts must pass `structure_problems` and `citation_problems` before its flags count, and the supplied text must remain present before its flags are evaluated; at least 9 of the 10 detailed and at most 2 of the 10 clean pass.
- AC-04 links three new incidents, then expects 409 `CONFLICT` for linking two of them again and for a member not UnderAssessment, 400 on `incident_ids` for a self-link (the spec's `uniqueItems`) and a single ID, 404 for an unknown member and 403 for Board, each with stored data unchanged; the determination on one member comes last, dated the latest member's discovery date, since no member can be determined before its own. AC-05 tags one item with all five categories in one request and reads them back as Board, then expects 400 on `impact_categories` for "misc", "misc" among valid ones and a repeat, and the approver's tag replaces the five. AC-19 expects `8-K Item 8.01`, no due date and `voluntary_disclosure` true for NotMaterial with `voluntary_disclosure`, and 400 on `voluntary_disclosure` for true with Material or a non-boolean.

- `AC-16-FPI-draft-is-6-K` prepares a separate FPI session on the failure stub and verifies a controlled four-element advisory 6-K draft, owned citations and an unchanged incident. If its child-session LLM reset fails, the parent run settles it before the next case.
- The six `AC-23-draft-*` cases reject Responder/Board acceptance, accept once with preserved content/incident and one checked audit entry, reject a repeat, reject an unknown draft, and enforce cross-session isolation. They share one generated Proposed draft and use the existing HTTP and snapshot helpers. Successful drafting/acceptance compares the shared Incident fields through `spec.declared_fields`, allowing extra metadata such as an embedded drafts list. Proposed and Accepted responses may omit optional acceptance metadata. Supplied values are checked, while the mandatory audit records the acting user and a checked timestamp. Audit payloads may omit old null acceptance metadata or include extra fields; their draft/status transition and supplied values are checked.


## Rules

- Never import `app`. The tester checks systems, ours included, only through their HTTP API; `tests/test_tester.py` fails on any `app` import here.
- Test-control errors carry `message` and `source`, never the project `Error` schema.
- HTML-escape everything `pages.py` shows from a report or the query: messages quote other teams' systems.
- The 501 catch-all matches every path, so declare every other route before it.
- Each storage function is one short transaction. A run never holds a transaction open while it calls the target.
- Settings are read on first use, not at import, so the tester still loads without `TESTER_DATABASE_URL`. Preview deployments don't have it, so setup, run and report answer 500 there; setup does so after the target has already prepared its session, since it stores ours only afterwards.
- `get_tester_settings()`, `get_engine()` and `_session_factory()` are cached. A test that changes `TESTER_DATABASE_URL` clears all three before and after.
- Nothing here creates tables; the tester role can't. `scripts/setup_db.py` creates `tester_sessions` from `models.py`, and a new tester table also needs a `TESTER_GRANTS` entry there. Changing a column needs a wiped local database or a migration, as for the app's tables (root "Local setup steps").
- Expected statuses, error codes and fields come from `system-openapi.yaml`, and each case's pass rule from its course acceptance criterion. For example, Responder and Board get 403 on the audit and delete routes, and only a DisclosureApprover gets 405.
- Each rejection case's request has exactly one thing wrong with it, so its expected error doesn't depend on the order a system checks errors in. A refused move to AmendmentPending sends `info_available_date` today and `elements: ["impact"]`, a subset of the latest filing's `unavailable_elements` wherever the incident has a filing. From a state reached without a filing (`FILED` lists those with one), `elements` can't be a subset of a filing that doesn't exist, so those AC-06 cases also pass a 400 `VALIDATION_ERROR` on `elements` with the incident unchanged.
- Dates in the cases assume the session's `test_now` is the setup default, `SETUP_TEST_NOW` (2026-10-05T15:00:00Z, whose date is `TODAY` in `cases.py`), so the runner's setup must send `setup: {}`, and a case may move the clock only inside `clock_at`.
- Make every project call through `Run.call`, never `Target.call`, and every test-control call through `Run`'s `snapshot`, `set_clock`, `set_llm` and `prepare`: `call`, `set_clock` and `set_llm` end the saved snapshot baseline, so a rejection is never compared with stale data. Change a session's `llm_base_url` only inside `llm_at`.
- Build HTTP clients for a target only through `runner.client_for`, so tests can serve `FakeSystem` there instead of the network.
- Test IDs are stable and unique, and start with their criterion (`AC-06-DM-to-Closed`); reports from both teams are compared by them.
- `spec.py` reads `system-openapi.yaml` and `tester-openapi.yaml`, and `planned()` reads `fixtures/`, on first use, not at import, so a missing file fails only the run, not the app.
